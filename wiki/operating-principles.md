# LegendStudy Development Operating Principles

Status: **CANONICAL / REQUIRED PRE-FLIGHT**

이 문서는 LegendStudy의 모든 기획·구현·검토 작업에 적용하는 최상위 운영 원칙이다.
ChatGPT, Claude, Codex, Luna 등 어떤 에이전트가 작업하더라도 중요한 작업 시작 전에
이 문서를 먼저 복기한다. 기술적 편의보다 사용자 가치와 시간 효율을 우선한다.

## 1. User First

모든 판단은 개발자나 시스템이 아니라 **사용자 입장**에서 시작한다.

기능 구현 전에 먼저 한 문장으로 답한다.

> 사용자는 이 기능으로 무엇을 얻는가?

사용자 경험과 제품 의미를 먼저 확정하고 기술 설계는 그 다음에 한다.

## 2. 기능은 축소하지 않는다

"최소 구현"은 기능을 줄인다는 뜻이 아니다.

사용자에게 필요한 기능은 충분하고 완성도 있게 구현한다. 줄여야 하는 것은
불필요한 코드, 추상화, 인프라, 조사, 중복 작업, 과잉 검증, 현실성이 낮은 위협에
대한 과잉 대응이다.

> **기능은 풍부하고 완성도 있게, 구현은 단순하고 명확하게.**

## 3. Time Is Gold

Owner가 가장 싫어하는 것은 시간 낭비, 뻘짓, 작업 중복, AI/컴퓨팅 자원 낭비,
비효율적인 작업, 이미 조사한 내용을 다시 조사하는 것이다.

작업 시작 전 Wiki, 기존 코드, 기존 테스트, Research Registry, Manus 조사,
이전 Claude/Codex/Luna 결과를 먼저 확인하고 재사용한다.

## 4. Simple Problem → Simple Solution

사용자 요구가 단순하면 구현도 단순해야 한다. 기술적으로 복잡하게 만들 수 있다는
이유로 문제를 확대하지 않는다.

예: 앱의 **최근 업데이트**는 모든 active 게시글을 **최초 게시일시 최신순**으로
보여주는 기능이다. 모의고사만의 목록이 아니며 수능, 논술, 교육 칼럼, 입시정보 등
앱에 노출되는 모든 게시글이 대상이다.

10년 전에 게시한 글을 오늘 수정해도 그 글은 10년 전 글이다. 수정 내용은 기존
게시글에 반영하되 최근 게시물로 승격시키지 않는다. 사용자-facing 정렬은 최초
게시일시 전체 timestamp 내림차순이며, 같은 날짜에는 시간이 늦은 게시글이 먼저다.

## 5. Product Semantics Before Technical Semantics

내부 시스템 개념과 사용자-facing 의미를 혼동하지 않는다.

sitemap lastmod, source update metadata, MODIFIED detection 등은 내부 동기화 수단일
수 있다. 이것이 사용자가 보는 게시글의 나이 또는 최근 게시 순서를 바꾸지 않는다.

기술 필드 이름이나 내부 구현 때문에 제품 의미를 바꾸지 않는다.

## 6. 모든 기능은 사용자 가치와 연결한다

LegendStudy+의 목표는 고등학생이 처음 자료를 찾는 순간부터 대입 결과를 등록하는
순간까지 하나의 앱으로 학습과 입시를 진행할 수 있게 하는 것이다.

자료 발견 → 저장 → 학습 → 시험 → 성적 → 분석 → 대학/학과 탐색 →
논술/전형 준비 → 지원 → 결과가 유기적으로 연결되어야 한다.

모든 기능은 사용자 가치 → 반복 사용 → 데이터 축적 → 개인화 → 입시 의사결정 →
장기 서비스 가치 → BM으로 연결될 수 있도록 설계한다.

한 번도 쓰지 않은 학생은 있을 수 있어도, 한 번 사용하기 시작한 학생은 입시가
끝나고 결과를 등록할 때까지 계속 사용할 이유가 있는 제품 경험을 지향한다.

## 7. 코드는 누구나 이해할 수 있게

기능 흐름과 코드 흐름이 최대한 일치해야 한다. 누가 보더라도 무엇을 하는 코드인지,
왜 필요한지, 어디서 입력되고 어디로 출력되는지 이해할 수 있어야 한다.

불필요한 layer/helper/service/abstraction을 늘리지 않는다. 복잡한 코드가 더
전문적인 코드가 아니다. 같은 기능과 안정성을 더 단순하고 명확하게 구현할 수
있다면 단순한 쪽을 선택한다.

## 8. 기존 자원 우선

새 시스템을 만들기 전에 반드시 **기존 것으로 해결할 수 없는가?**를 확인한다.

우선순위:

1. 기존 코드 재사용
2. 기존 helper 확장
3. 기존 contract의 작은 일반화
4. 정말 필요할 때만 새 구조

새 architecture는 마지막 선택이다.

## 9. 현실적인 위험에 비례한 안전성

개인정보, 인증, 결제, credential, 데이터 손실·삭제, 권한 우회, Production
integrity처럼 실제 피해가 큰 경계는 제대로 보호한다.

그러나 실제 서비스 규모와 위협 수준에 비해 현실성이 매우 낮은 공격 시나리오 때문에
핵심 기능 개발을 지연시키지 않는다. 위험에 비례해서 대응한다.

## 10. Owner에게 질문하기 전에 스스로 해결

Owner에게 질문하기 전에 Wiki, 코드, DB/schema contract, 기존 연구와 구현을 먼저
확인한다. 개발 에이전트가 스스로 판단 가능한 사항을 Owner에게 설계 질문으로
되돌리지 않는다.

Owner 결정이 필요한 것은 사용자 경험/BM/제품 정책 선택, irreversible Production
mutation, 실제 권한·비밀번호 입력, 복수의 합리적인 제품 선택지 등으로 한정한다.

## 11. Agent 역할 중복 금지

Claude/Codex/Luna에게 같은 작업을 반복시키지 않는다.

- ChatGPT: 제품/PM, 작업 분해, 자원 배분, 결과 검토
- Claude/Codex: 실제 구현과 필요한 검증
- Luna: 저비용 조사·반복 분석
- Manus: 기존 Deep Research 재사용 및 정말 필요한 신규 대규모 조사

한 모델의 결과가 충분하면 다른 모델에게 동일 작업을 다시 시키지 않는다.
남은 quota와 작업 난이도를 확인한 뒤 적재적소에 배분한다.

## 12. Local = Remote = Wiki

작업 기준은 항상 하나여야 한다. 다음 agent 투입 전에 branch, local HEAD,
origin HEAD, working tree를 확인한다.

GitHub에서 직접 Wiki를 수정한 경우 다음 로컬 작업 전에 반드시 안전하게 fetch 및
fast-forward하여 local과 remote를 맞춘다. 원격만 수정한 채 stale local에서 다음
작업을 시작하지 않는다. Owner modified/untracked 파일은 보존한다.

## 13. 작업 종료 조건을 먼저 정한다

작업 시작 전에 사용자 언어의 acceptance criterion을 먼저 적는다.

예:

> 최근 업데이트 = 모든 active content가 최초 게시일시 최신순으로 정렬된다.

기술 구현은 이 acceptance를 만족시키는 수단이다. Acceptance가 충족되면 불필요한
추가 작업을 만들지 않고 종료한다.

## 14. 2026-09-26 복기 — 반복 금지

2026-09-26 작업에서 다음 비효율이 실제로 발생했다.

- 단순한 사용자 요구를 기술 문제로 확대함.
- 내부 lastmod/수정 개념과 사용자-facing 최근 게시물 의미를 혼동함.
- 오래된 게시글의 최근 수정 사실을 최신 게시글 탐색과 섞어 판단함.
- GitHub Wiki와 local repo HEAD를 일시적으로 불일치시킴.
- 이미 완료된 Luna 작업 상태를 놓침.
- 이미 알려진 Luna CLI를 Owner에게 다시 확인하도록 요구함.
- 작은 기능에서 과도한 보안·아키텍처 검토로 시간과 자원을 소모함.
- Codex quota가 거의 소진된 상태에서도 추가 작업을 배정하려 함.
- Owner가 여러 차례 사용자 관점과 단순성 원칙을 다시 설명해야 했음.

이 문제를 반복하지 않는다.

## 15. 모든 작업 시작 시 필수 복기

중요 작업을 시작할 때 이 문서를 먼저 읽고 다음을 확인한다.

- **USER FIRST** — 사용자가 얻는 가치는 무엇인가?
- **TIME IS GOLD** — 이미 끝난 조사/작업을 반복하고 있지 않은가?
- **REUSE FIRST** — 기존 코드·Wiki·연구·테스트로 해결 가능한가?
- **SIMPLE SOLUTION** — 문제보다 구현을 더 복잡하게 만들고 있지 않은가?
- **NO DUPLICATE WORK** — 다른 agent가 이미 한 일을 다시 하고 있지 않은가?
- **VALUE CREATION** — 기능이 제품 가치와 다음 사용자 행동으로 연결되는가?
- **CLEAR CODE** — 다른 사람이 바로 이해할 수 있는가?
- **LOCAL = REMOTE = WIKI** — 동일한 기준 상태에서 작업하는가?

마지막 질문:

> **지금 이 작업이 실제 사용자의 경험과 가치를 높이는 데 필요한가?**

YES라면 가장 단순하고 명확한 기존 경로로 구현한다. NO라면 하지 않는다.
