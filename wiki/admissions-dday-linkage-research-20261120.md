## 결론과 집계 기준

- 운영 지원 기록은 **14건: 2027학년도 수시 13건 + 정시 계획 1건**이다. 수시 중 논술 6건, 다른 전형 6건, 전형 확인이 필요한 계획 1건이다. 수시 12건은 지원/단계합격 상태, 1건은 계획 상태다.
- **기존 LAB의 구조화 일정 + 공식 모집단위 표를 대조한 논술 날짜 연결 후보는 4건**이다. 이화 1건은 선택한 논술 유형 확인 조건부, 서울과기 1건은 기존 공식 일정 데이터가 부족하다. 이는 사람이 근거를 확인한 후보 수이며, 현재 자동 매칭/등록 기능이 있는 건수는 **0건**이다.
- 공식 원문을 논술 외 일정까지 읽으면 **11개 수시 지원 기록에 대응할 합격자 발표 근거 후보**가 있다. 기존 JSON에는 없는 확장 자료이며, 중앙의 기회균형 세부전형·서강의 학교장추천 정식 명칭 등 정규화 검수가 필요하다. 11건을 자동 등록 가능한 확정 건수로 표시하지 않는다.
- 4건은 지원 기록 단위이고, 11건과 겹친다. 합산하여 15개 지원으로 세지 않는다. 같은 학생의 같은 공식 발표를 여러 지원이 참조할 수 있으므로 실제 D-Day 카드 수는 별도로 중복 제거해야 한다.
- 공식 자료가 없는 날짜, 여러 후보 중 특정 날짜/캠퍼스/시험 유형, 학생의 실제 합격·응시 여부는 추정하지 않는다. 등록일 2026년과 입학 학년도 2027을 혼동하지 않는다.

## 실제 구조 조사 A–J

| 항목 | 확인한 상태와 재사용 범위 |
|---|---|
| A. 지원 DB | `student_applications` 14행, `student_application_events` 30행. `user_id`, `admission_year`, `university_id`, 대학명 snapshot, `admission_type`, `admission_name`, `intended_division`, revision/시각 보유. 전형·모집단위는 자유문자열이며 정규 ID, 캠퍼스, 학생 선택 시험유형은 없다. |

| C. LAB 일정 | WEB `essay-university-schedules.json`: 2027학년도 25개 대학 key, 62행. 공식 URL/확인시각/페이지/SHA256·캠퍼스·계열·날짜·일부 구간 보유. 공개 Catalog의 legacy offerings와 합쳐 표시한다. 모든 대학/전형을 검증한 자료는 아니다. DB `essay_exams` 478행의 `exam_date`는 전부 NULL. 이 테이블은 과거 문제 회차이며 현재 입시 일정 저장소로 전용하지 않는다. |
| D. 대학 UUID | 14/14 지원의 대학 FK 유효. 수시 13/13은 LAB Catalog의 canonical university UUID와 연결된다. 중앙 DB slug `chungang` ↔ Catalog source key `cau`이므로 문자열 slug만으로 조인하면 누락된다. 고려 서울/세종·연세 서울/미래처럼 대학 UUID만으로 캠퍼스를 결정할 수도 없다. |
| E. 세부 구분 | LAB `track`은 주로 인문/자연·교시 설명이며 지원 전형 ID가 아니다. 대학·학년도·캠퍼스·정식 전형·모집단위별 적용 범위를 검수한 매핑이 필요하다. 원문 표는 있으나 현재 자유문자열만으로 전부 결정할 수 없다. |
| F. 관리자 | 기존 WEB admin에 대학 일정 등록/수정/검수/배포 UI와 해당 DB RPC가 없다. 일정은 정적 파일 수정과 WEB 배포로 갱신한다. 관리자 지원 조회는 기존 `admin_applications_list`를 재사용할 수 있다. |
| G. 실제 매칭 | 아래 14건 대조표. 같은 대학의 논술 날짜를 기회균형/고른기회 면접에 사용하는 것은 오매칭이다. |
| H. 재사용 | Auth/profiles/universities, 지원 저장·정정·이력 RPC, 공식 일정 근거, `day_targets`, Home 카드/관리 sheet, 기존 관리자 권한 재사용. |
| I. 추가 DB/RPC | 공식 일정과 정정 revision, 지원 매칭 근거, 학생별 삭제/복원 의사, 기존 D-Day와의 연결이 필요하다. 파일만 고쳐서는 여러 기기 동기화·삭제 후 미재생성·운영자 일정 수정이 충족되지 않는다. 아래는 후보 설계이며 SQL 미작성/미적용. |
| J. WEB/APP | WEB의 기존 지원 폼·상태 UI와 관리자 일정 관리, APP 기존 D-Day 모델/저장소/관리 sheet 확장. APP 전체 지원 편집기나 신규 Home 레이아웃은 MVP 필수가 아니다. 현재 APP 지원 영역은 조회 위주이며 WEB이 지원 편집을 제공한다. |

실제 DB에서 관련 public 테이블은 `day_targets`, `student_applications`, `student_application_events`만 확인했다. 기존 지원 RPC는 `my_applications`, `my_application_events`, `my_application_save`, `my_application_event`, `my_application_delete`이다. D-Day/공식 일정 동기화 RPC는 발견되지 않았다. 학생 지원 DB에는 SELECT만 부여하고 쓰기는 RPC 경로, D-Day는 authenticated 직접 CRUD + owner/lifecycle RLS 경로다. 이 차이를 배포 호환성 설계에 반영해야 한다.

현재 조사로 날짜를 채우지 못한 행은 결측으로 남긴다. 정확한 시각이 없는 날은 `date`만 보유하며 00:00 시험 시작으로 변환하지 않는다. 원문의 ‘예정’, 기한/기간, 입실 시각과 실제 시험 시각을 각각 보존한다.

## 저장 설계 전 일곱 보존 검토

1. **발생·기록·정정**: 공식 고사/발표 날짜, 대학 공지 시각, 검수/게시 시각, 학생 삭제/복원 시각은 다른 사실이다. 기존 지원 이벤트의 occurred_at/recorded_at과 D-Day 날짜를 혼용하지 않는다.
2. **재현 근거**: 원문 URL/페이지/SHA256/공식 확인 시각, 학년도/캠퍼스/전형/모집단위 범위, 당시 지원 revision과 매핑 규칙 revision을 기록한다. 공개 원문 보존은 기존 근거 저장 방식을 재사용하며 학생 원문과 분리한다.
3. **UPDATE 손실**: 공식 일정 정정은 새 revision으로 남기고 Home 표시만 갱신한다. 학생 삭제 의사는 별도 기록으로 보존한다. 현재 지원 삭제 RPC가 지원·이벤트를 물리 삭제하는 기존 한계는 그대로 기록하며 이번 기능에서 전체 지원 삭제 정책을 바꾸지 않는다.
4. **동일 주체**: 기존 profiles/Auth UUID로만 소유자를 결정한다. WEB/APP는 같은 소유자 데이터를 사용하고 학년·연도가 바뀌어도 다른 계정으로 만들지 않는다.
5. **Decision/Outcome**: 지원은 자기보고 Decision, 일정은 외부 공개 사실, D-Day는 표시용 파생값이다. 발표일 도래로 accepted/rejected/stage_pass 이벤트를 생성하거나 응시 사실을 추정하지 않는다.
6. **목적·권한·보존**: 개인 일정 편의만을 위한 최소 연결 정보. 관리자 공식 일정 편집권과 학생 지원 원문 접근권을 분리한다. 자격 세부사유/수험번호/학교 성적 신규 수집 불필요. 삭제 기억도 계정 생명주기에 종속되며 계정 삭제 후 영구 보존하지 않는다. 새 개인정보 테이블은 기존 계정 삭제/탈퇴 gate와 함께 검증한다.
7. **파생값 구분**: D-n/매칭/카드수는 derived이며 원본 날짜·지원 사실을 덮어쓰지 않는다. 미확정/다중 후보와 규칙 버전을 남기고 확률 점수나 AI 추정으로 자동 등록하지 않는다.

## 권장 DB와 매칭 구조 — 후보, 미설치

`공식 일정 revision + 기존 지원 revision → 검증된 연결 → 학생의 삭제/복원 의사 → 기존 day_targets`

기존 `day_targets`를 Home 표시 컬렉션으로 계속 사용한다. 다음은 필요한 데이터 역할이며 최종 DDL은 구현 승인 뒤 제약조건/기존 스키마를 재확인해 작성한다.

| 역할 / 후보 이름 | 최소 계약 |
|---|---|
| 공식 사건 `admission_schedule_events` | 날짜/배열 순서와 무관한 stable UUID. 대학 UUID, 학년도, 캠퍼스, 사건 종류(논술·면접·발표), 회차/단계. 현재 revision 참조. 공식 취소/철회는 삭제 대신 상태 전환. |
| 원문·정정 `admission_schedule_revisions` | append-only revision. 공식 출처/페이지/hash/검수자·시각, `event_date`/구간/시각의 정확도, verified/draft/withdrawn, 적용 전형·모집단위의 명시적 범위, 이전 revision. 공통 일정은 검증된 대상 집합으로 표현한다. NULL을 모든 전형으로 해석하지 않는다. |
| 지원 연결 `application_schedule_links` | 기존 application+owner 복합 FK, application revision, 공식 사건/revision, 정규화한 전형·모집단위·캠퍼스/선택유형, 규칙 버전, matched/needs_confirmation/unmatched 사유. UNIQUE(application,event). 원문 입력은 보존한다. |
| 개인 표시 의사 `student_schedule_preferences` | UNIQUE(owner,event), active/dismissed 상태·revision, nullable `day_target_id`, 적용 원문 revision. 표시 가능 여부와 사용자 삭제 의사를 별도로 둔다. application을 지웠다고 이 행을 cascade하여 삭제 기억까지 없애지 않는다. |
| 최소 작업 이력 `student_schedule_actions` | 자동 생성/출처 변경/학생 삭제/복원 사유·시각·revision/request_key. 별도 분석 플랫폼 대신 이 기능의 동시성/복원 추적에 필요한 기록만 보유. 계정 삭제 계약에 종속. |

새 전형/학과 전체 마스터 시스템부터 만들 필요는 없다. 검수한 연도·대학·캠퍼스 범위 안의 공식 명칭과 명시적 별칭을 우선 사용하고, 자유입력 원문은 지원 테이블에 남긴다. 별칭만으로 결정되지 않는 경우 기존 WEB 지원 폼에서 선택 확인을 받는다. ‘학교장추천’을 전국 공통 ‘지역균형’으로 바꾸는 규칙은 금지한다.

매칭 조건은 대학 UUID + 학년도 + 수시 + 캠퍼스 + 검증된 전형 + 모집단위 적용 범위 + 필요한 시험 유형/단계다. 한 학생의 여러 지원이 **같은 공식 사건**을 가리키면 하나의 D-Day에 연결한다. 같은 날짜라도 다른 전형/시험/발표는 합치지 않는다. 공식 범위가 나뉘는 정정은 이전 사건의 승계 관계와 삭제 의사 승계를 검수해야 하며 새 ID로 우회 재생성하지 않는다.

### RPC·권한·동기화

- 기존 `my_application_save/event/delete`의 revision/멱등성/소유자 계약 유지. 성공한 지원 변경과 공식 일정 게시를 서버 동기화의 입력으로 삼는다. 주기적 누락 복구는 같은 멱등 처리 경로를 호출한다. 클라이언트가 켜져 있어야만 생성되는 구조로 만들지 않는다.
- 후보 RPC: `my_admission_day_events`(상태/출처 조회), `my_admission_day_event_dismiss/restore`(소유자/expected revision/request_key), `admin_admission_schedule_preview/publish`(검수·영향 미리보기/게시). 공식 일정 게시와 학생 동기화를 구분해 재시도 가능하게 한다.
- 서비스 내부 동기화 함수는 일반 authenticated 직접 실행을 허용하지 않는다. 공개 관리자 RPC는 기존 `admin_users`/관리자 helper를 서버에서 확인한다. 학생 RPC는 `auth.uid()` 및 기존 lifecycle lock/allowed 검증, 새 테이블은 owner RLS와 직접 쓰기 제한을 적용한다. service_role 키를 브라우저/APP에 노출하지 않는다.
- 한 owner/event에 대해 삭제·복원·자동 갱신을 같은 잠금 순서로 직렬화하고 unique 제약으로 중복 방지. source revision CAS로 오래된 작업이 최신 날짜를 되돌리지 못하게 한다. 사용자 삭제가 갱신과 경합하면 최종 dismissed가 우선한다.
- 기존 APP는 `day_targets`에 직접 DELETE한다. **신규 RPC만 만드는 것으로 삭제 후 미재생성을 보장할 수 없다.** 자동 연결 행의 성공한 직접 삭제도 같은 트랜잭션에서 삭제 의사로 기록하는 제한된 trigger/호환 경로가 필요하다. 내부 철회/지원 소멸에 따른 projection 제거는 사용자 삭제와 구분하고 클라이언트가 내부 사유를 위조할 수 없어야 한다.
- 자동 일정의 공식 날짜/출처를 구버전 클라이언트가 직접 변경하는 경로는 서버에서 차단하고 설명 가능한 오류를 반환한다. 수동 일정 CRUD와 자동 일정의 대표 지정은 유지한다. 개인 날짜로 바꾸려면 명시적으로 수동 복사 후 자동 일정 삭제를 제공하는 방향이다.
- 원래 수동 일정은 내용이 같아도 자동 연결로 탈취/병합하지 않는다. `is_primary`는 학생 선택이며 자동 생성/날짜 변경으로 빼앗지 않는다. 현재 APP 대표 변경은 clear/set 두 요청이므로 새 동기화와의 경합 검증이 필요하다. 원자적 대표 변경 RPC를 도입한다면 수동 일정 회귀도 함께 확인한다.
- 대학 사이트 변경 감지와 게시된 공식 데이터의 학생 반영을 구분한다. **MVP: 관리자가 공식 변경을 검증·게시 → 관련 D-Day 자동 갱신**. 후속 모니터는 변경 의심 자료를 검수 대기로 보낼 수 있으나 PDF 자동 해석만으로 게시하지 않는다. 현재 전 대학 변경 감지 Worker는 없다.

## 학생 UX와 정책

Owner 확정 정책은 실제 지원 기반·4요소 매칭·공식 일정만·삭제/미재생성/복원·공식 변경 반영·수동 기능/Home 구조 보존이다. 다음 세부 동작은 그 정책을 구현하기 위한 **권장안**이며 승인된 운영 동작으로 서술하지 않는다.

| 상황 | 권장 동작 |
|---|---|
| 지원 저장/수정 | 지원 완료/단계합격 등 실제 지원 상태만 자동 연동. 계획은 일정 후보 안내만. 원래 지원 정보를 자동 정정하지 않는다. |
| 공식 날짜 확정 | 오늘/미래의 검증된 단일 날짜만 초기 생성. 범위만 있거나 학생별 날짜가 미정이면 확인 대기. 과거 일정을 초기 일괄 생성하지 않는다. |
| Home | 기존 대표 + compact 2개/더보기 구조, KST D-n, 대표 선택을 유지. 자동 여부의 상세 설명은 기존 관리 sheet에서 제공. |
| 관리 sheet | ‘지원 일정’ 표시, 대학·전형·모집단위·학년도·원문 링크/확인일, 삭제/대표 지정. 기존 수동 추가/수정/삭제 유지. 자동 날짜는 공식 정보로 표시. |
| 학생 삭제 | D-Day 표시 제거 + dismissed 저장. 지원 원문/공식 일정은 보존. “자동으로 다시 추가되지 않으며 복원할 수 있음”을 안내. |
| 재동기화/날짜 수정/지원 재등록 | 같은 공식 사건의 dismissed 유지. 다른 기기/재로그인/Worker 재시도에서도 재생성하지 않는다. |
| 학생 복원 | 관리 sheet의 ‘삭제한 지원 일정’에서 명시적으로 복원. 당시 날짜 대신 최신 verified revision으로 재연결. 근거 철회/대상 변경이면 복원 불가 이유 표시. |
| 공식 날짜 변경 | active만 최신 날짜로 갱신, 변경 전후/출처 안내. dismissed는 숨긴 채 최신 근거만 연결. 사건 ID 유지. |
| 공식 취소/출처 충돌 | 새 날짜를 추정하지 않고 표시를 보류하고 관리 sheet에 확인 필요 사유. 사용자 삭제 상태는 유지. |
| 지원 삭제/전형 변경 | 해당 연결 해제. 다른 유효 지원 연결이 있으면 유지, 마지막 연결이 없어지면 자동 표시 제거. 이를 사용자 삭제로 오인하지 않되 기존 dismissed는 보존. |
| 발표일 도래 | D-DAY/지난 일정 표시만 갱신. 학생 결과/합격/불합격 기록은 변경하지 않는다. |

APP 제목 제한은 현재 **15 code point**, DB는 80자다(저장소의 과거 ‘20’ 주석은 실제 상수와 다름). 짧은 표시명과 전체 근거 표시를 분리하고 자동 제목을 잘라 전형 의미가 뒤섞이지 않도록 한다. 알림·푸시·캘린더 앱 연동은 이번 MVP에 포함하지 않는다.

## 구현 우선순위와 예상 일정

한 명의 구현 담당자 기준 **8–12 근무일 + 공식 자료 보완 2–5일 정도**의 계획 추정이다. 승인·외부 자료 확보·APP 실제 기기 검수 대기 시간은 별도이며, 11/22 고사 전에 제공할 수 있다는 약속이 아니다. 개발 시작 때 이미 지난 날짜는 다시 판정해야 한다.

| 순서 | 범위 | 추정 |
|---|---|---|
| P0-1 | 14건 매핑 검수: 이화 선택 유형, 중앙 세부전형, 서강 명칭, 국민 입력, 서울과기 공식 원문. 오늘자/후속 변경 공지 확인. | 자료 2–5일, 학생 확인은 별도 |
| P0-2 | 최소 DB/RPC, RLS/lifecycle·삭제 기억·동시성·구버전 호환. 검증 SQL/원복 계획을 만든 뒤 AGENTS §4 승인 절차. | 2–3일 |
